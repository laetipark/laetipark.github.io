# 프로젝트 작업 가이드

이 문서는 Laetipark 포트폴리오 작업을 시작할 때 사용하는 문서 라우터입니다. 루트의 [AGENTS.md](../AGENTS.md)와 [CLAUDE.md](../CLAUDE.md)는 이 문서로 안내하는 역할만 하며, 프로젝트 규칙의 정본은 `docs/rules/`에 둡니다.

[저장소 소개와 실행 방법](../README.md) · [화면 목업과 검증 기록](design/portfolio-redesign.md) · [프로젝트 근거 자료](design/project-sources.md)

## 시작 순서

1. 현재 요청의 변경 범위와 영향을 받는 파일을 확인합니다.
2. 아래 표에서 해당하는 규칙 문서를 모두 선택해 읽습니다.
3. 선택한 문서를 기준으로 구현하고 가장 좁고 유효한 검증을 수행합니다.
4. 동작이나 작업 방식이 달라졌다면 같은 변경에서 정본 문서도 갱신합니다.

## 문서 선택표

| 문서                                 | 담당 범위                     | 읽는 경우                          | 기본 검증            |
| ------------------------------------ | ----------------------------- | ---------------------------------- | -------------------- |
| [프론트엔드 규칙](rules/FRONTEND.md) | React/Vite 구조와 구현        | 컴포넌트, 화면, 라우팅, 상태, 타입 | lint·build           |
| [디자인 규칙](rules/DESIGN.md)       | UI, CSS, 토큰, 반응형, 접근성 | 레이아웃, 스타일, 테마, 상호작용   | 브라우저 확인·build  |
| [Figma 구현 규칙](rules/FIGMA.md)    | Figma 디자인의 코드 변환      | Figma 노드, 자산, 디자인 번역      | lint·build·시각 비교 |
| [API 규칙](rules/API.md)             | Chat Laetus 클라이언트 계약   | 환경 변수, 요청·응답, 오류 처리    | 관련 상태·lint·build |
| [배포 규칙](rules/DEPLOYMENT.md)     | GitHub Pages와 Actions        | 워크플로, 배포 경로, SPA 복구      | build·설정 교차 확인 |

각 검증의 실행 조건과 명령은 해당 규칙 문서를 따릅니다. 화면별 목업과 실제 확인 결과는 [디자인 개편 기록](design/portfolio-redesign.md)에 모으고, 지속적으로 적용할 규칙은 위 정본에만 작성합니다.

프로젝트 목록을 추가하거나 설명·이미지를 바꿀 때는 프론트엔드와 디자인 규칙을 함께 읽고 [프로젝트 근거 자료](design/project-sources.md)에 원본 링크를 연결합니다.

## 함께 읽는 조합

- 일반 UI 변경: [프론트엔드 규칙](rules/FRONTEND.md) + [디자인 규칙](rules/DESIGN.md)
- Figma 기반 UI 구현: [Figma 구현 규칙](rules/FIGMA.md) + 프론트엔드 규칙 + 디자인 규칙
- Chat Laetus 통신 변경: [API 규칙](rules/API.md) + 프론트엔드 규칙, 화면도 바뀌면 디자인 규칙 추가
- GitHub Pages 경로나 Actions 변경: [배포 규칙](rules/DEPLOYMENT.md), 앱 라우팅도 바뀌면 프론트엔드 규칙 추가
- 여러 범주에 걸친 변경: 관련 문서를 모두 읽고 각 문서의 검증 항목을 합쳐 수행

## 규칙 우선순위

규칙이 충돌하면 아래 순서를 따릅니다.

1. 사용자의 현재 명시 요청
2. 선택한 `docs/rules/*.md`
3. 이 작업 가이드
4. 루트 라우터 파일

같은 우선순위의 규칙이 충돌하면 더 구체적인 범위를 다루는 문서를 우선하고, 판단이 결과를 크게 바꾼다면 작업 전에 사용자와 확인합니다.

## 공통 완료 기준

- [ ] 작업 범주에 맞는 규칙 문서를 모두 읽었습니다.
- [ ] 변경한 동작, 실제 설정과 문서 설명이 서로 일치합니다.
- [ ] 코드 변경이면 해당 규칙이 요구하는 lint, build와 수동 확인을 수행했습니다.
- [ ] UI 변경이면 모바일·데스크톱, 라이트·다크와 키보드 상호작용을 확인했습니다.
- [ ] API 변경이면 설정 누락, 성공·오류 응답과 선택 필드 조합을 확인했습니다.
- [ ] 배포 변경이면 `/`와 `/chat`의 직접 접근과 새로고침 흐름을 확인했습니다.
- [ ] 문서 변경이면 로컬 링크, 참조 경로와 명령어가 실제로 존재하는지 확인했습니다.

## 문서 유지 체크리스트

- 새 규칙은 가장 가까운 `docs/rules/` 정본 한 곳에만 작성합니다.
- 다른 문서에서는 같은 내용을 복사하지 않고 상대 링크로 연결합니다.
- 새 규칙 문서를 만들면 이 문서의 선택표와 조합에 연결합니다.
- 파일 경로, 명령어, 환경 변수, 요청 예시는 실제 저장소와 대조합니다.
- 코드 동작을 바꾼 변경은 관련 문서를 같은 작업에서 갱신합니다.
- 오래된 규칙은 방치하지 않고 삭제하거나 대체 문서로 연결합니다.
- 문서만 바꾼 경우 빌드는 생략할 수 있지만 링크, 경로, 명령어와 Markdown 형식은 직접 확인합니다.
